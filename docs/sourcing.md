# 出典の集め方

『超かぐや姫！』で実際にやって分かったことを、作品を変えても使える形で残す。
一般論ではなく、**この作品で試して通った／通らなかった**ことを書いている。

原典（脚本・シナリオ）が手に入らない前提なので、集める作業は
「原典にどれだけ近い資料に届くか」の勝負になる。

## 1. 出典の階層

上から順に探す。上に行くほど強いが、上だけでは量が足りない。

| 階層 | 例 | 出典種別 |
|---|---|---|
| 作品そのもの | 本編・原作小説・コミカライズ・公式ガイドブック | 手元の資料として `add-text` |
| 本編の書き起こし | セリフ集・字幕・名言集 | `transcript` |
| 公式の言明 | 公式サイト、公式SNS、監督・スタッフ本人の投稿 | `official_site` / `official_sns` |
| 取材されたもの | 監督・キャストのインタビュー | `interview` |
| 報じられたもの | 紹介記事、ニュース、まとめ記事 | `article` |
| 本編の読み取り | 時系列整理、地図考察、設定の突き合わせ | `fan_chronicle` |
| 百科事典 | Wikipedia、作品Wiki、ピクシブ百科事典 | `wiki_index` |
| 解釈 | 感想note、考察ブログ、Q&Aサイト | `fan_note` |
| 図表の中身 | 記事に貼られた表・カレンダー・地図の画像 | `image_transcript` |

**書籍・雑誌・ラジオが出典の情報**は、ネット上に辿る先が無い。
Wikipediaの脚注がその入口になることが多い（後述）。

## 2. 探す順序

1. **公式サイトを丸ごと**。トップに登場人物・あらすじ・スタッフが揃っていることが多い。
   `/news/` `/music/` `/theater/` などの下層も見る（JSで描画されていて本文が取れないことがある）。
2. **版元の商品ページ**。小説・コミカライズ・ガイドブックのページには、公式のあらすじと
   「何が補完されているか」が書いてある。KADOKAWAなど。
3. **Wikipediaを索引として開く**。記事本文より**脚注の外部リンク**が本体。
   `cqs wiki refs <sv>` で一覧、`cqs wiki fetch-refs <sv>` で未取得を取り込む。
   本作では脚注92件から外部URL80件が取れ、そこから11件を原資料として取り込めた。
4. **インタビューを検索**。「作品名 監督 インタビュー」「作品名 キャスト インタビュー」。
   媒体ごとに聞いている内容が違うので、複数媒体を取る価値がある。
5. **本編の書き起こし**。「作品名 セリフ」「名言」「名シーン」。
   全文トランスクリプトは（本作では）見つからなかったが、名言集は
   **キャラクターごとにセリフが引用されている**ので、口調・関係性の根拠として効く。
6. **時系列・設定の整理記事**。「作品名 時系列」「考察」「まとめ」。
   これは感想ではなく本編の読み取りなので `fan_chronicle` に入れる（3節）。
7. **薄いエンティティを埋める**。`cqs entity coverage` で出典数の少ない人物を見つけ、
   その人物名で検索し直す（6節）。

## 3. 媒体ごとの取り方

本作で実際に試した結果。

| 媒体 | 結果 | やり方 |
|---|---|---|
| 公式サイト | ○ | そのまま取得。下層ページはJS描画で空のことがある |
| X（旧Twitter） | ○ | **FxTwitter API 経由**。`https://x.com/<user>` でプロフィール、`/status/<id>` で投稿本文・投稿日時・引用元・反応数。タイムラインは辿れないので投稿URLを個別に渡す |
| note | ○ | そのまま取得 |
| はてなブログ | ○ | そのまま取得。**表やカレンダーが画像**のことが多い（5節） |
| Wikipedia | ○ | 索引として使い、脚注を辿る |
| 作品Wiki（atwiki等） | ○ | 人物ページが公式より詳しいことがある |
| KADOKAWA商品ページ | ○ | 版元なので `official_site` 扱い |
| ニュース系（電ファミ、映画.com、アニメ！アニメ！、ciatr、にじめん、Gamer） | ○ | UAを変えると通ることがある |
| Yahoo!知恵袋 | ○ | 回答は玉石混交。`fan_note` 扱い |
| ピクシブ百科事典 | **×** | 403。手元のブラウザからコピーして `add-text` |
| natalie.mu | **×** | 405（UAを変えても不可） |
| Netflix作品ページ | **×** | JS描画で本文が取れない |
| fusetter / privatter | **未検証** | ふせったーは本文が動的。取得できなければ手元でコピーして `add-text --kind fan_note` |

取得の設定（robots.txt・User-Agent・アクセス間隔）は README の「取得の設定」を見る。

### 脚注を辿るときの注意

`wiki fetch-refs` は脚注を機械的に辿るので、**その作品の範囲外の記事まで入る**。
『魔法少女まどか☆マギカ』では、スピンオフゲーム（マギアレコード、Magia Exedra）の
記事・公式サイト・ゲーム内イベントの告知が混ざった。ゲームのキャラクターや
ガチャの記述が、本編の人物についての質問で上位に来る。

取り込んだあと `cqs sources` を見て、作品の範囲から外れるものは
`cqs source-kind` で下げるか、別の作品DBに分ける。
**どこまでを1つの作品とするか**（TVシリーズだけか、劇場版・ゲーム・スピンオフを含むか）は
最初に決めておくほうがよい。DBは作品ごとに分かれているので、分けるのは安い。

一方、脚注からは良いものも入る。同じ作品では公式サイトの用語解説ページ
（見滝原町・見滝原中学校・使い魔）が脚注から見つかった。トップページからは辿れない階層だった。

## 4. 取れなかったときの回避策

- **403 / 405 で弾かれる**: まず `CQS_USER_AGENT` を変えてみる。それでも駄目なら、
  手元のブラウザで本文をコピーして `cqs add-text --kind <種別> --url <元のURL>`。
  URLを渡しておけば出典としては同じ扱いになる。
- **JSで描画されていて本文が空**: 同上。取得した文字数が異常に少ない版（数十字）は疑う。
- **書籍・雑誌・ラジオが出典**: Wikipediaの脚注に書名・号数が載っていることが多い。
  `cqs wiki annotate <sv>` で、どの主張がどの脚注に基づくかを主張のメモに残せる。
  URLの無い脚注は「ネット上に辿る先が無い」印になる。
- **表や図が画像**: `cqs images list / save / transcribe`（5節）。

## 5. 表と画像

- HTMLの `<table>` は行ごとに畳んで取り込まれる（`・見出し: 値 / 見出し: 値`）。
- **記事の要の情報が画像になっていることがある**。本作では作中の時系列表と
  カレンダーがどちらも画像で、代替テキストは空だった。本文には
  「時系列表を用意しました」としか書かれておらず、対応表そのものが見えていなかった。

      cqs -w <作品> images list <sv>        # 本文に属する画像を一覧
      cqs -w <作品> images transcribe <sv>  # Claudeに読み取らせて原文層へ（APIキーが要る）
      cqs -w <作品> images save <sv>        # キーが無ければ保存して自分で読む

  読み取り結果は `image_transcript`（確認状態は常に「伝聞」）として入る。
- 取り込みの仕方を直したときは `cqs rederive` で、**取得し直さずに**保存済みの生データから
  本文を作り直せる。

## 6. カバレッジで回す

    cqs -w <作品> entity coverage --kind character

件数だけでなく**いくつの出典から来ているか**を見る。出典が1〜2件しかないエンティティは、
主張が多くても同じ情報の言い換えである可能性が高い。

本作では、彩葉の家族（父・母）が物語の軸なのに主張1〜3件だった。
人物名で検索し直して考察記事とWikiの人物ページを足したら、1件→17件・3件→10件になった。

一方、脇役は天井が低い。諌山真実は出典を足しても11件で止まった。
**ネット上にその人物について書かれた情報が、公式プロフィールの言い換えしかない**ためで、
これは仕組みの問題ではない。その場合は公式ガイドブックなど書籍に当たるしかない。

## 7. 分類の落とし穴

- **ホスト名で公式かどうかを決めない**。`x.com` を一律「公式SNS」にすると、
  ファンの投稿が「公式確認」として入る。公式アカウントは
  `cqs rule "x.com/<アカウント名>" official_sns` のようにアカウント名まで指定する。
- **「ファンが書いたもの」を一括りにしない**。解釈（「彩葉はかぐやを娘のように見ていた」）と
  本編の記述（「卒業ライブは2030年9月12日」）は別物。後者は `fan_chronicle`（伝聞）に入れる。
  でないと作中の日付を問う質問に答えられなくなる。
- **同じ記事に観察と解釈が混ざる**場合は、支配的なほうで出典種別を決め、
  個別の主張の確認状態を `cqs claim set-verification` で直す。
- **分類を間違えたら** `cqs source-kind <出典ID> <種別>` で直せる。
  既存の主張の確認状態は自動では変わらない（人手で付けた判断を潰さないため）。
- **名言まとめサイトを「書き起こし」に入れない**。書き起こしは台詞を順に写したもので、
  名言まとめは投稿者が選んだ断片の一覧。後者は `fan_chronicle` に入れる。
  優先度が75と40で大きく違い、間違えると本編の記述が押しのけられる。
- **姓名の間の空白**は無視して突き合わせている（「諌山真実」と「諌山 真実」）。
  それ以外の表記ゆれは `cqs entity add <正規名> --alias <別名>` で登録する。

## 8. 関連作品が複数ある作品世界（区分）

TVシリーズ・劇場版・スピンオフゲームが並ぶ作品では、**同じ登場人物の同じ問いに、作品ごとに違う答えがある**。
結末、生死、関係、設定のどれもが分岐しうる。確からしさ（確認状態）とは別の軸なので、
出典ごとに「どの作品についての記述か」を持たせる。これを区分と呼ぶ。

```
cqs -w <作品> segment rule "madoka-magica.com/tv"        "TVシリーズ"
cqs -w <作品> segment rule "madoka-magica.com/rebellion" "劇場版 叛逆の物語"
cqs -w <作品> segment set 17 "マギアレコード"     # ルールで拾えないものは手で
cqs -w <作品> segment list                        # 区分ごとの出典数
```

- 区分名は作品ごとに自由に決める。定義済みの語彙ではない。
- URLで機械的に分かるものはルールにする。ルールは新規取得時に自動で当たり、
  `segment apply` で既存の出典にも当て直せる。
- まとめ記事・Wikipedia・公式のシリーズ紹介など、どの作品とも言えないものは
  「シリーズ全体」のような区分に置く。空にしておくと「区分不明」と区別が付かない。
- 区分は回答時のプロンプトに入り、「区分の違う主張を、区分を伏せたまま同じ作品の事実として並べない」
  という制約になる。ブラウザUIでは主張のバッジと絞り込みに出る。

**1作品しか無いならこの軸は使わない**。区分の付いた主張が1件も無ければ、プロンプトにも
UIにも出ない。原作小説とアニメで筋が違う、といった場合には1作品でも使える。

## 9. 回答が薄いときに疑うところ

「情報量が少ない」と感じたら、素材が無いのか、素材はあるのに届いていないのかを先に分ける。

```bash
cqs -w <作品> ask "<質問>" --no-llm | head -60   # 実際に渡っている材料を見る
```

- **同じ出典ばかりが並ぶ** → その出典が節ごと選ばれている。名言まとめのように、
  見出しに人物名が付いた断片の集まりだと起きやすい。出典種別を疑う（上の分類の落とし穴）。
- **公式やWikipediaの説明文が1件も無い** → その記述が主張として登録されていないか、
  登録されていても届いていない。`cqs -w <作品> claims "<語>"` で知識層にあるかを確かめる。
- **知識層には無かった** → 原文層にはあるかもしれない。`cqs -w <作品> search "<語>"` で探し、
  あれば `cqs propose <版ID> --register` を掛け直す。
- **そもそも検索語が取れていない** → `cqs -w <作品> ask "<質問>" --no-llm --json` の
  `terms` を見る。漢字1文字＋送り仮名の語（「願い」「月」）が中心の質問では、
  ここが空になっていないかを確かめる。
- **一覧表ばかりが並ぶ** → 材料の取り出しは節を単位にしている。節の見出しが
  登録済みのエンティティと一致すると押されるので、その対象（魔女名、用語、地名）を
  `cqs entity add` で登録してから `rebuild_claims.py` を掛け直す。
- **「それぞれの〜」に答えられない** → 数え上げの質問は、どの一人ひとりを指すのかが
  質問文に書かれていない。ブラウザUIのLLM前処理が名前を補うと届くようになるので、
  対象を全部エンティティとして登録しておく（前処理には登録名の一覧を渡している）。
- **原文層にも無かった** → 素材が足りない。Wikipediaの記事は「○○の登場人物一覧」
  「○○のエピソード一覧」のように分割されていることが多い。本体記事の
  「→詳細は「...」を参照」が次に取るべき記事を教えてくれる。

まどマギでは、主要人物の関係を訊いた回答が薄かった原因が3つ重なっていた。
名言まとめサイトが材料の9割を占めていたこと、キャラクター一覧・エピソード一覧・劇場版の
各記事を取っていなかったこと、そして人物名が節見出しにしか無い文が抽出から落ちていたこと。

## 10. 資料を広げる

「情報が薄い」の多くは素材不足なので、まず数を入れる。ただし入れ方を分ける。

**作品そのものを説明する資料**（公式サイト、Wikipediaの本体・キャラクター一覧・エピソード一覧・
各劇場版・外伝の記事、書き起こし）は丸ごと入れる。人物名を含まない文（用語・設定・各話・
制作の経緯）も主張になる。

**作品に言及しているだけの資料**（監督・脚本・声優・音楽家・制作会社の記事、原典の古典）は
`entity_only` にする。触れる文だけを採るので、その人の他作品の話が流れ込まない。

```bash
cqs -w <作品> source-extract <出典ID> entity_only
cqs -w <作品> segment set <出典ID> "制作・出演者"
```

広げる前に **エンティティを足しておく**。抽出は節見出しの人物名を文に引き継ぐので、
登録されていない名前は節ごと落ちる。用語（ソウルジェム、円環の理）、魔女や怪物の名前、
関連作品名、主題歌名、声優名まで入れると、検索の効き方が変わる。
まどマギでは34→93件に増やしたところで、「それぞれの魔女化」の質問が
3/7から7/8に上がった（エンティティ登録だけの効果）。

エンティティを足したら `rebuild_claims.py` を掛け直す。主張とエンティティの
結び付きは登録時に決まるので、後から足しても既存の主張には付かない。

### 取れない媒体の回避

| 媒体 | 直接取得 | 回避策 |
|---|---|---|
| pixiv百科事典 | ×（403、UAを変えても不可） | 検索API（Firecrawl）が返す本文を `add-text` で入れ、`--note` に経路を書く |
| fandom.com / www*.atwiki.jp | ×（403） | `w.atwiki.jp` 配下は取得できることがある |
| 公式サイトの特集ページ（JS描画） | ×（HTMLに本文が無い） | 未解決。ブラウザで描画してから取る仕組みが要る |
| Netflix作品ページ | ×（JS描画） | 同上 |

## 11. 抽出の規則を変えたとき

見出しの取り方や、どの文を採るかを変えたら、**原文と主張を作り直す**。

```bash
python examples/rebuild_claims.py <作品スラッグ>    # 原文を作り直し、自動抽出の主張を入れ直す
python examples/backfill_offsets.py <作品スラッグ>  # 原文中の位置を埋め直す
python examples/eval_basic_facts.py <作品スラッグ>  # 基本的な事実が材料に入るか確かめる
```

`rebuild_claims.py` は `note` の付いた主張（手で足したもの、専用の取り込みで作ったもの）を
残し、自動抽出ぶんだけを作り直す。位置（offset）は原文での並び順に使うので、
取り込み直したら必ず埋め直す。埋めないと、後から入った文が記事の末尾にあることになり、
時系列やあらすじの切り出しが壊れる。

## 12. 運営が続くゲームを扱うとき（学園アイドルマスターで分かったこと）

映像作品と違い、**内容が増え続ける**。取り込みは1回では終わらないので、
何をどこから取ったかをスクリプトに残す（`examples/ingest_gakumas_official.py`）。

### どこに何があるか

| 欲しいもの | あった場所 | 無かった場所 |
|---|---|---|
| 人物のプロフィール | 公式サイトの人物ページ（構造が固い） | — |
| ゲームシステムの仕様 | 攻略Wiki（Gamerch・seesaawiki） | **公式サイトの紹介ページはJS描画で本文が空** |
| 親愛度STEPの構成・解放条件 | 非公式wiki（seesaawiki）の人物ページ | 公式 |
| コミュの中身 | ファンの「振り返り」記事（note）。話数と台詞つき | **完全な書き起こしは見つからない** |
| 3D描画・演出・AI・基盤の技術 | **CEDECの講演と、その報告記事** | 開発元の技術ブログ（作品名の記事が無い） |
| 開発の裏話・ボツ案 | 取材記事。非公式wikiの「WEB記事一覧」が索引になる | — |
| 生放送で何が発表されたか | 公式の「お知らせまとめ」記事。wikiの配信一覧が索引 | — |

- **技術の話は技術ブログに無いことがある**。CEDECの講演ページ（概要・講演者・
  メッセージ）と、それを書き起こした媒体の記事（1本2万字に達する）のほうが厚い。
- **非公式wikiに索引ページがあれば、それはWikipediaの脚注と同じに使える**。
  「WEB記事一覧」「公式配信一覧」から辿ると、取材記事と公式告知がまとめて手に入る。
  URLを控えるのではなく、索引ページから辿るようにすると更新に追従できる。
- **ページ一覧が頭打ちになるwikiがある**（seesaawikiは100件）。メニューの
  リンクを辿ると、一覧に出ない80ページ以上が見つかった。
- **EUC-JPのwikiがある**。本文だけでなくURLもEUC-JPでパーセント符号化する。

### 1人について書かれたページ

人物ページは**本文に名前が出ない**。「広にとっては『初めてできた友達』。」が
誰の話か分からなくなる。題名から主語を決めて帰属させる取り込みを書く
（`ingest_subject_page`）。「定期公演『初』/篠澤広」のように題名の後ろに
名前が付く形もあるので、`/` で切った末尾も見る。

### 固有名詞をエンティティにするときの落とし穴

**他の語の一部になる名前を入れない**。学園アイドルマスターでは、
全体曲「初」が「初めて」「最初」「初星」に当たって1,741件の主張に誤って
紐づいた。校歌「標」は「目標」に当たって496件。曲名・カード名を機械的に
登録するときは、2文字以下の名前を除くか、実際の紐づき件数を見て判断する。

用語も同じで、難易度の「プロ」は「プロデュース」「プロデューサー」に当たる。
`難易度プロ` のように、本文に実在する長い形で持つ。

### 何を入れないか

## 13. 新しい作品を立ち上げるときの手順

1. `cqs new "作品名"`
2. `cqs rule` で、その作品の公式ドメインと公式SNSアカウントを登録する
2b. 関連作品が複数あるなら `cqs segment rule` で区分を先に決める（後からでも当て直せる）
3. `cqs entity add` で主要な人物・用語を別名つきで登録する（これを先にやらないと抽出が空振りする）
4. 公式サイトを取得し、構造が分かる節（登場人物欄など）は専用の取り込みを書く
   （`examples/ingest_cho_kaguyahime.py` が例）
5. Wikipediaを取得し、`wiki refs` → `wiki fetch-refs` で原資料へ広げる
6. インタビュー・書き起こし・時系列整理を足す
7. `images list` で図表の画像を確認し、必要なら読み取る
8. `entity coverage` で薄い人物を見つけ、その人物名で検索し直す
9. 実際に質問を撃ってみる。答えられない質問が、次に足すべき出典を教えてくれる
