# 設計メモの再チェックと、実装して変えた点

対象: [`design.md`](design.md)（2026-09-01）
検証: 本リポジトリの実装と、『超かぐや姫！』の実データ投入（出典15件・主張472件）による。

## 1. そのまま成立した点

実装して動作を確認できたもの。

- **3層分離（原文層・知識層・回答層）**。原文層を不変にしたことで、再取得時に本文ハッシュを比べるだけで
  「その出典に依存する主張を要再確認へ落とす」処理が機械的に書けた（`store.add_version`）。
- **出典種別から確認状態を機械的に決める**。公式サイト→公式確認、感想note→ファン解釈が
  そのまま実装できた（`constants.SOURCE_KINDS`）。人が上書きすることもできる。
- **ツール形式（MCP）を初日から固定する**。UIを作らずにClaude Desktop / Claude Codeから引ける。
  中核は設計どおり `search_claims` / `search_sources` / `get_source` の3つで足りた。
- **SQLite FTS5**。追加ライブラリなしで動く。件数が増えてもコードは変わらない。
- **Deep Researchの二段構え**。実データで検証した。意図的に誤りを混ぜた報告
  （「かぐやの声優は花澤香菜」）を公式サイトと照合させたところ一致率40%、
  欠落語として「花澤香菜」が挙がり、正しい主張（一致率100%）と区別できた。

## 2. 設計から変えた点

### 2.1 知識層の実体を「git管理のMarkdown」から作品DB（SQLite）へ

設計メモ8章は知識層をgit管理のMarkdownに置くとしていた。これを、原文層と同じ作品DBの中に移した。

理由:

1. **作品ごとにDBファイルを差し替える**という要件と両立しない。Markdown＋gitだと、
   作品の追加が「ディレクトリを足してgit運用を決める」ことになり、ファイル1つで完結しない。
2. **リポジトリが公開である**。二次情報から抽出した主張と原文スナップショットは第三者の文章に由来するので、
   公開リポジトリのgit履歴に載せたくない。DBファイルなら `.gitignore` 1行で分離できる。
3. 原文層と知識層が別ストアだと、主張が指す出典ID（`source_version_id`）の整合性を自前で守る必要がある。
   同一DBなら外部キーで担保できる。

失うもの: gitの差分・巻き戻し・ブランチ。代替として、上書き履歴（`claims.status` と `claim_links`）と
作業ログ（`activity_log`）をDBに持たせた。ただし「1行直して差分を見る」体験は再現していない。
Markdownエクスポートは実装していない（必要になった時点で足す）。

### 2.2 「矛盾あり」を確認状態から外し、主張間の関係にした

設計メモは確認状態の選択肢に「矛盾あり」を入れていた。これは1件の主張の属性ではなく2件の関係なので、
`claim_links`（`contradicts` / `supersedes` / `supports`）に分けた。

確認状態に混ぜていると「公式サイトの記述だが、別の公式記述と食い違っている」が表現できない。
分けたことで、確認状態は「どれだけ確かか」だけを表し、矛盾は「どれとどれが」を表すようになった。

### 2.3 「改訂＝有効期限または改訂番号」を状態＋上書きリンクにした

有効期限は運用できない。誰がいつ期限を切るのかが決まらず、期限切れの主張をどう扱うかも決まらない。
代わりに `status`（`active` / `superseded` / `retracted`）と、新旧を結ぶ `supersedes` リンクを置いた。
検索は既定で `active` だけを返し、`--all` で履歴も辿れる。

### 2.4 エンティティの別名（表記ゆれ）を追加

設計メモに項目が無かったが、日本語では必須だった。公式サイトのプロフィール本文は
「酒寄彩葉」と「彩葉」を混在させる。別名を持たないと、正規名で登録した主張が略称で引けない。
`entity_aliases` を足し、抽出時にも別名で拾って正規名へ寄せている。

### 2.5 全文検索は trigram ＋ 2文字語の LIKE 併用にした

設計メモ6.3の「人物名・用語名は表記が固定されやすく、キーワード一致で当たる」は、
**FTS5の既定トークナイザでは成り立たなかった**。

- 既定の `unicode61` は空白で語を切るため、日本語の本文はほぼ1語として索引化され、部分一致で引けない。
  → `tokenize='trigram'` に変更した。
- trigram は**3文字未満を索引化しない**。本作の登場人物は「彩葉」「芦花」「真実」「乃依」と2文字が多く、
  これらが一切引けない。→ クエリを3文字以上の語と2文字以下の語に分け、前者はFTS索引、
  後者は `LIKE` で併せて絞る実装にした（`textutil.split_terms`）。

個人利用の文量では `LIKE` の併用で速度は問題にならない。設計メモの「規模で実装を変えない」方針は保っている。

### 2.6 取得の作法（robots.txt とアクセス間隔）を分けた

設計メモに記述が無かった。当初は robots.txt を既定で確認する実装にしたが、
それによって Wikipedia・X・Netflix・一部記事サイトが取得できず、
とくに**公式SNSが原文層に入らない**という実用上の穴が出た。

そこで二つを分けた。

- **アクセス間隔（同一ホストへ既定1.5秒）は常に有効**。相手サイトへの負荷を決めるのはこちらなので切れない。
- **robots.txt の確認は既定で行わない**（`CQS_RESPECT_ROBOTS=1` で有効化）。

加えて、`405` や接続リセットで弾かれるサイト向けに `CQS_USER_AGENT` を差し替えられるようにし、
途中で切られた応答（`IncompleteRead`・打ち切られたgzip）も読めたぶんだけ原文層に入れるようにした。

### 2.7 「AI調査報告は根拠にできない」をDBの不変条件にした

設計メモでは運用上の約束だったが、`store.add_claim` が出典種別 `ai_report` の版を根拠にした主張を
拒否するようにした。アプリ側の約束ではなくストアの制約なので、CLI・MCP・Web UIのどこから触っても破れない。

### 2.8 出典の優先順は主張に持たせず、出典種別から導いた

設計メモ3.3は「出典の優先順を知識層の項目として持たせ」としていたが、優先順は出典種別から一意に決まるので、
主張ごとに持つと不整合の原因にしかならない。`constants.kind_priority` で導出し、検索結果に添えて返している。

## 3. 実装して分かった、設計メモに無かった問題

### 3.1 文単位の自動抽出は帰属を誤る

公式サイトの登場人物欄には「彩葉のことが大好き。」という文がある。これは**かぐや**のプロフィールの一部だが、
文だけを見ると主語が無く、素朴に抽出すると「酒寄彩葉についての主張」になってしまう。

対策として、節の構造が分かっている出典には専用の取り込みを書き、
キャラクターごとに帰属を付けてから主張にした（`examples/ingest_cho_kaguyahime.py`）。
構造が分からない出典（インタビュー・感想note）は文単位の抽出のままにしてある。

一般解は「抽出はLLMに任せる」（設計メモ3.2の記述どおり）。作品固有のパーサは、
構造が安定していて件数が多い出典にだけ書くのが妥当と判断した。

### 3.2 作品名に終止符が含まれると文分割が壊れる

『超かぐや姫！』は題名自体が「！」で終わる。句点・感嘆符で機械的に文を切ると、
「アニメ「超かぐや姫！」と切れて断片が量産された。括弧の内側では切らないようにして直した
（`textutil.split_sentences`）。日本語の作品名では珍しくない形なので、作品を問わず効く。

### 3.3 感想noteが件数として多数派になる

投入した472件の内訳は、公式確認74件・記事のみ107件・ファン解釈291件。ファン解釈が6割を占める。
確認状態で区別しているので回答の質は歪まない（ファン解釈は「そう述べる感想がある」としてしか使われない）が、
検索の上位が感想で埋まると公式記述が埋もれる。検索結果は確認状態の順（公式→記事→ファン解釈）に
並べ替えるようにした（`store.search_claims`）。

### 3.4 文だけを取り出すと、その文が何についての記述かが失われる（3.1の一般化）

3.1では公式サイトの登場人物欄について書いたが、同じ欠陥がすべての出典で起きていた。
症状がはっきり出たのは、作中の時系列を整理したファン記事を取り込んだときである。

記事は `<帝が挑戦状を吹っかけてきた日>` のような節見出しの下に本文が続く構造だった。
文単位で抽出すると見出しが落ちるので、知識層には

    メールの日付から8月16日だと分かります。

という主張だけが残る。**8月16日に何があったのかが書かれていない**ので、
これを何件集めても時系列は組み立てられない。実際「作品内の時系列を箇条書きで」という質問に対し、
回答は「時系列表の存在は分かるが中身は取り込まれていない」という答えになった。
記事は取得できており、文も66件登録されていた。落ちていたのは見出しだった。

同時に二つの欠陥も見つかった。

- **箇条書きが丸ごと落ちていた**。句点で終わらない行は断片として捨てていたため、
  記事の結論にあたる「・彩葉とかぐやが一緒に居たのは7/11〜9/12」が知識層に入っていなかった。
- **文中の「？」で文が切れていた**。「プロゲーマーとFPS？でガチンコ対決し」が2つの主張に割れていた。

対処として `extract.candidate_sentences` を行単位の処理に変え、
節見出し（`<...>`、`【...】`、`#` 見出し、句読点を含まない短い行）を覚えて主張に冠するようにした。
見出しが入れ子で続く場合は繋ぐ（「かぐや / 声 - 夏吉ゆうこ」）。
箇条書きの行は1項目を1つの主張として扱い、句点で終わらなくても落とさない。
終止符の直後が「で」「と」「が」などの接続なら文を切らない。

結果、同じ記事から

    帝が挑戦状を吹っかけてきた日: メールの日付から8月16日だと分かります。
    卒業ライブ: 2030年の9/12はリアルでも満月です。

が得られるようになった。Wikipediaのあらすじ節も同様に `あらすじ:` を冠した順序どおりの主張になり、
回答側のプロンプトに「同じ出典の主張は claim ID の小さい順が原文の並び順に対応する」と明記した。

### 3.5 「感想note」は二つの別物を混ぜていた

設計メモは二次情報を「公式／記事／感想note」の三段で分けていたが、実際に作品の内容を調べると、
ファンが書いたものの中に性質の違う二種類があった。

- **解釈**: 「彩葉はかぐやを娘のように見ていた」— 書き手の読み方。他人が検証できない。
- **本編の記述**: 「卒業ライブは2030年9月12日。かぐやがブレスレットを渡したのは20時58分（部屋の時計）」
  — 本編を見れば当たっているかどうか確かめられる。

両方を「ファン解釈」に入れると、後者が「そう解釈する感想がある」としてしか使えなくなり、
作中の日付や設定を問う質問にまったく答えられない。逆に両方を事実扱いにすると解釈が事実に混ざる。

そこで出典種別に `fan_chronicle`（ファンによる本編の記述・時系列整理）、
確認状態に `secondhand`（伝聞）を足した。伝聞の扱いは
「作中の出来事として述べてよい。ただし公式が述べたことではなく本編を見た第三者の読み取りなので、
出典を示し、他の出典と一致するかどうかを断る」。優先順は 記事のみ ＞ 伝聞 ＞ ファン解釈 とした。

分類は書き手ではなく書かれ方で決める。同じブログでも、時系列の整理は `fan_chronicle`、
結末の意味の考察は `fan_note` に入れる。

### 3.6 出典種別をホスト名で決めると公式を誤認する

`x.com` を一律「公式SNS」に対応づけていたため、ファンの投稿が「公式確認」として取り込まれた。
ホスト名では誰のアカウントかは分からない。既定をファン扱いに変え、公式アカウントは
作品ごとのルールでアカウント名まで指定する形にした（`x.com/Cho_KaguyaHime` → `official_sns`）。

取り込んだ後に分類を直せるよう `cqs source-kind` を足した。既存の主張の確認状態は自動では変えない
（機械的に上書きすると人手で付けた判断を潰すため）。

### 3.7 一発検索では、質問の語と本文の語が噛み合わない

「かぐやが月に帰ってしまった日付は？」に答える記述は、本文では「卒業ライブ」「2030年の9/12はリアルでも満月」
と書かれている。質問文の語で引いても当たらない。

設計メモ6.1がツール形式（MCP）を選んだ理由がここにある。LLMが「人物名で引いて足りなければ出来事名で引き直す」
往復をできるなら解決する。一方、CLIの `ask` とブラウザUIは一発検索なので当たらない。

対処として、(a) 検索の点数付けを「エンティティ一致で埋め尽くす」形から
「エンティティ一致＋語一致の合算」に変え、人物名を含まない記述（日付・設定の文）が埋もれないようにし、
(b) `retrieve(extra_terms=...)` で検索語を外から足せるようにした。
公開したブラウザ版では、質問の前に短い呼び出しで検索語を組み立ててから引いている。

### 3.8 一発検索は「文を拾い集める」形では順序の質問に答えられない

3.7で検索語の補助を足したが、それでも「作品内の時系列を箇条書きで」に答えられなかった。
測ると `retrieve` は**0件**を返していた。原因は二つで、性質が違う。

**(a) 質問文をまるごと全文検索に渡していた。** `search_claims(query=質問文)` は
質問文全体を1つのフレーズとして扱うため、ほぼ必ず0件になる。
漢字・カタカナ・英数の連なりを語として取り出す `question_terms` を通すようにした。

**(b) 文単位のキーワード一致では、順序が答えになる質問は原理的に解けない。**
「時系列を出せ」に対し、知識層にある答えは「かぐやを拾った日: …」「ミニライブの日: …」
という**並び**であって、「時系列」という語を含む文ではない。語で拾うと、
記事の前書き（「時系列順にまとめました」）だけが当たって本体が落ちる。

そこで検索の単位を文から**節**へ広げた。当たりが集まった出典については、
その出典の主張を原文の並び順（=claim IDの順）ごと取り出す。
これを素朴に実装すると次の副作用が出たので、順に潰した。

| 症状 | 対処 |
|---|---|
| 「作品」のような頻出語が点数を支配し、「時系列」がかき消される | 語の重みを出現件数で割る（多く当たる語ほど軽く）。全部落ちた場合は上位2語を残す |
| 主張数の多い出典（Wikipedia 400件）が弱い当たりの積み上げで勝つ | 出典の点数を主張数の平方根で割る |
| 出典のタイトルが「…詳細な時系列」でも、当たりが少ないと選ばれない | タイトルが検索語を含む出典に加点し、当たりが少なくても節として採れるようにする |
| 感想noteの節が公式・記事の節を押しのける | 出典種別の優先順を出典の点数に掛ける |
| 節が材料を食い尽くし、「かぐやの声優は？」の答えが埋もれる | 節の取り分を全体の6割までにし、並びを「点で効く主張 → 節 → 残り」にする |

加えて、矛盾関係にある主張は片方が入ったら相手も必ず入れるようにした。
片方しか渡らないと「矛盾する場合は両方を並べる」という約束が守れず、
実際に「対立する主張の中身はこの知識層に無い」という回答が出ていた。

### 3.9 表と画像の中身が、どこにも入っていなかった

原文層はHTMLから本文テキストを作っているが、次の二つが抜けていた。

**(a) 表はセルを縦に並べただけになっていた。** `<table>` を単なるブロック要素として扱っていたため、
Wikipediaの興行収入表は「1週目の週末（2月20日・21日・22日）」「5位」「14.81」「2.91」が
別々の行になり、行と列の対応が失われていた。値だけの行は句点で終わらないので、
知識層にはそもそも入らない。表を行ごとに畳み、見出し行があれば「見出し: 値」の対で書き出すようにした。

    ・週: 1週目 / 順位: 5位 / 累計興収: 2.91

**(b) 画像の中身は代替テキストしか取れていなかった。** 作中の時系列をまとめた記事では、
**カレンダーと詳細な時系列表がどちらも画像**で、しかも代替テキストは空だった。
記事本文には「時系列表を用意しました」としか書かれておらず、日付と出来事の対応表そのものは
システムから完全に見えていなかった。

画像を扱う経路を足した（`cqs images list / save / transcribe`）。
`transcribe` は画像を取得してClaudeに読み取らせ、結果を出典種別 `image_transcript`（画像の読み取り）
として原文層に入れる。機械が画像を読む工程が挟まる以上、確認状態は常に「伝聞」になる。
元の記事のどの画像から来たかは主張のメモに残す。

これで「かぐやが月に帰った日」に対して、記事本文の断片ではなく表の行そのものが引けるようになった。

    表: 2030年9月の詳細な時系列表（9/2〜9/22）: 9/12(木): 時系列=かぐやが月に帰る /
    出来事=卒業ライブ / 20:58 ブレスレットを渡す / 21:00 卒業ライブ / 22:49 ウォレット入金

**副産物: 原文層の「不変」の意味がはっきりした。** 描画の仕方を直したとき、取得し直さずに
保存済みの生データから本文を作り直せる必要がある（`cqs rederive`）。
原文層が保存しているのは取得したバイト列そのものであって、`text` はその描画結果にすぎない。
不変なのは前者で、後者は作り直してよい、と整理した。
この過程で、X はHTMLではなくFxTwitterのJSONを保存していることを見落とし、
JSONをHTMLとして解釈して本文を壊す不具合を出した。生データの形を見て描画を選ぶよう直した。

### 3.10 情報の厚みは、エンティティごとに大きく偏る

主要人物と脇役では、集まる主張の数が2桁違う。実測すると、かぐや1011件に対し諌山真実11件。
これは抽出や検索の不具合ではなく、**そもそも脇役について書かれた二次情報が少ない**。
公式サイトの5行を、Wikipediaも紹介記事も言い換えているだけ、という状態になる。

そこで `cqs entity coverage` を足した。エンティティごとに、主張の件数だけでなく
**いくつの出典から来ているか**と確認状態の内訳を出す。出典が1〜2件しかないエンティティは、
どれだけ主張があっても同じ情報の言い換えである可能性が高い。

    名前                 主張   出典   公式   記事   伝聞   感想
    かぐや              1011   51   35  374  251  351
    諌山真実               11    5    6    3    2    0
    酒寄朝久               10    2    0    0   10    0

この指標で薄い箇所を見つけ、その人物を扱った出典（声優インタビュー、キャラクター個別のWiki、
家族関係を扱った考察）を足す、という回し方になる。
実際、酒寄紅葉（彩葉の母）は1件→17件、酒寄朝久（父）は3件→10件になった。

**ここで、姓名の間の空白による取りこぼしも見つかった。** 出典によって「諌山真実」「諌山 真実」と
表記が割れ、Wikipediaの人物節の記述がその人物に紐づいていなかった。
名前を本文から拾うときは空白を無視して突き合わせるようにした（`textutil.flatten`）。

### 3.11 Wikiを根拠から外すと、書籍のみの情報が丸ごと落ちる

設計メモ4章は「Wikiは主張の根拠にせず、出典欄からリンク先を辿り原資料の方を取り込む」としていた。
辿る先がネット上にある限りこれは正しく、実際 Wikipedia の脚注から80件の外部URLが取れ、
そこから未取得の原資料を取り込めた（`cqs wiki refs` / `wiki fetch-refs`）。

しかし**出典が書籍・雑誌・ラジオしかない記述は辿る先が無い**。今回の作品では、
『an・an』2026年5月20日号、spoon.2Di vol.131、『ニュータイプ』2026年3月号、ラジオ番組を出典とする
記述が該当し、脚本の作り方・キャラクターの設定・キャスティングの経緯といった、
他のどこにも出ていない情報が含まれていた。Wikiを根拠から完全に外すと、これらは丸ごと落ちる。

そこでWikiの扱いを「根拠にしない」から「伝聞として根拠にできる」に変え、代わりに
**どの脚注に基づく記述かを主張のメモに残す**ようにした（`cqs wiki annotate`）。
URLのある脚注は「本来どの原資料に当たるべきか」を示し、URLの無い脚注は
「ネット上に辿る先が無い」ことを示す。今回は72件の主張に脚注が付き、うち5件が書籍・ラジオのみだった。

Wikiの第一の役割が索引であることは変えていない。索引としても使い、根拠としては伝聞どまりにする、
という二重の扱いにした。

### 3.12 「どの作品の記述か」は確認状態では表せない

設計メモは1つのDBを1つの作品に対応させていた。ところが『魔法少女まどか☆マギカ』のように
TVシリーズ・劇場版3本・スピンオフゲーム2本が同じ世界を共有する作品では、分け方が二通りある。
作品ごとにDBを分けると「ほむらは誰か」を全DBで重複して持つことになり、横断した質問ができない。
1つにまとめると、**劇場版の結末とTVシリーズの結末が、同じ確からしさの主張として並ぶ**。

問題は、この違いが既存のどの軸でも表せないことだった。確認状態は「どれだけ確からしいか」、
出典種別は「誰が書いたか」であって、どちらも「何についての記述か」ではない。
公式サイトの記述はどの作品のものでも `official` になる。

そこで出典に `segment`（区分）列を足した（スキーマ版2、`db.migrate()` で既存DBにも追加される）。
値は作品ごとに自由に決める文字列で、URLパターンからのルール推定と手動指定の両方を持つ。
主張は出典の区分を引き継ぎ、回答プロンプトには
「区分の違う主張を、区分を伏せたまま同じ作品の事実として並べない／区分をまたぐ食い違いは
矛盾ではなく作品ごとの違いとして扱う」という制約が入る。

矛盾検出（設計メモ7章）との関係で言うと、**区分が違う主張の食い違いは矛盾ではない**。
同じ区分の中での食い違いだけが矛盾として扱われるべきで、区分はそのための前提になる。

### 3.13 一致した場所（本文か見出しか）を区別していなかった

「暁美ほむらと鹿目まどかの関係は？」に対して、回答に渡る120件のうち**105件が名言まとめサイト**
から来ていた。知識層には Wikipedia のストーリー展開節（時間遡行の経緯を説明する連続した記述）が
入っていたのに、1件も届いていなかった。

原因は主張の形にある。主張は「節見出し: 本文」の形で保存される。名言まとめサイトの主張は

    By 鹿目まどか & 暁美ほむら（投稿者：涙様） / 魔法少女まどか☆マギカ名言: こいつは結界に隠れて身を守る必要なんてない。

となり、**セリフ本体は誰のことも名指ししていないのに、見出しのおかげでエンティティ一致として
満点を取る**。こうした主張が数百件あるので、点の合計で出典を選ぶと必ず勝つ。
見出しは「この主張が何の話題の下にあるか」であって「何を述べているか」ではないので、
見出しだけの一致は本文の一致の1/4に下げた。

### 3.14 出典の点数を出典全体で測ると、大きい出典の該当節が沈む

3.8で「大きい出典ほど弱い当たりが積み上がって有利になる」として主張の総数の平方根で割ったが、
これは逆の失敗を生んだ。Wikipediaの記事は1つの出典に800件以上の主張が入り、当たりは記事の
端から端まで散る。総和を √800 で割ると、該当節がどれだけ密でも点が残らない。

実際に回答へ渡すのは**連続した一区間**なので、出典全体ではなくその区間で比べるように変えた。
幅を固定した窓を主張の並び順に滑らせ、当たりの合計が最大になる位置を探す。幅が同じなので
出典の大きさで割る必要がなくなり、「800件のうち24件の区間にどれだけ当たりを詰められるか」で
小さい出典と正面から比べられる。切り出す区間もこの窓にした（以前は当たりの最小IDと最大IDの
中点を中心に取っていたので、当たりが散っている出典では無関係な場所が切り出されていた）。

### 3.15 題名一致の加点が中身の一致を上回っていた

出典の題名が検索語を含むときの加点を「語の重み（最低1.0）× 4」としていたため、「関係」のような
ありふれた語でも4点が付き、正規化後の本文一致（10〜25点）に対して大きすぎた。中身がほとんど
当たっていない記事が題名だけで節ごと選ばれていたので、重みをそのまま使い、総量に上限を置いた。

### 3.16 日本語の地の文は主語を繰り返さない

Wikipediaのキャラクター記事では、「暁美 ほむら」という見出しの下に7文あっても、
文中に名前が出るのは2〜3文しかない。残りは「劇中でその内面や過去などの秘密が明かされていく」
のように主語が省かれる。抽出は文だけを見てエンティティ判定をしていたので、これらが
丸ごと落ちていた。**節見出しが人物名なら、その節の文はその人物についての記述**として
エンティティを引き継ぐようにした（超かぐや姫！で+715件、まどマギで+159件）。

3.13の割引と組みで効く。見出し由来のエンティティは付くが、検索時の重みは本文一致より軽い。

### 3.17 「本編の書き起こし」と「名言まとめ」は別物だった

名言・名セリフまとめサイトを `transcript`（本編の書き起こし、優先度75）に分類していた。
書き起こしは本編の台詞を順に写したもので原典に近いが、名言まとめは投稿者が選んだ断片の一覧で、
順序も文脈も無い。優先度75は不当に高く、検索でも回答でも本編記述を押しのけていた。
`fan_chronicle`（優先度40）に直した。確認状態はどちらも伝聞なので、既存の主張は変わらない。

### 3.18 検索語の切り出しが日本語の内容語を捨てていた

3.7で「質問文をそのまま全文検索に渡すと0件になる」として語に割る処理を入れたが、
その正規表現が `[一-龥々]{2,}`、つまり**漢字2文字以上**だった。日本語の内容語は
漢字1文字＋送り仮名が非常に多い。

    「まどかはどんな願いを叶えた？」→ 検索語 []

「願い」は漢字1文字＋送り仮名、「叶えた」も同じ。取れる語が1つも無く、
エンティティ「鹿目まどか」だけで検索していた。作品の中心にある事実が
Wikipediaにも公式サイトにも書いてあるのに出てこない、という状態の主因はこれだった。
同様に「月」「夢」「敵」「死」「力」「声」のような1文字語が全部落ちていた。

漢字の連なりと、漢字1文字の語には送り仮名を足した形の両方を出すようにした。
「願い」からは `願` と `願い` の両方を出し、本文が「願う」でも「願い」でも当たる。
送り仮名を足すのは漢字1文字のときだけにした。2文字以上の語に続くのはたいてい助詞で、
「関係は」「時系列に」のような、本文には現れない語を作ってしまうため。
助詞（は・が・を・に・へ・も・の・で）は送り仮名として扱わない。
存在しない語は出現数0になり、重み付けの段階で自動的に落ちる。

「何」は疑問詞なので語の区切りとして扱う（「全何話」→「全」「話」）。
「教えて」「詳しく」「箇条書き」など、質問の言い回しでしかない語は除外した。

### 3.19 人物名にだけ重み付けをしていなかった

語は出現数で重みを変えていた（3.7）のに、エンティティ一致は一律4点だった。
主人公は数百件の主張に出てくるので、名前が一致してもほとんど何も絞り込めない。
「まどか」が443件、質問の鍵になる「願」が157件という状況で、名前のほうが高い点を
取っていたため、**答えそのものの主張が順位の外へ押し出されていた**。
人物にも語と同じ式を当て、出現件数から重みを出すようにした。
脇役（11件）は重く、主人公（443件）は軽くなる。

### 3.20 当たりが少ない質問で、材料が数件で終わっていた

「主題歌は？」のように語が1つしか取れず、その語の出現も少ない質問では、
上限120件に対して材料が5件しか集まらないことがあった。当たった文の前後には
答えの残りが書かれていることが多いので、材料が上限の半分に満たない場合は
当たりの前後3件ずつを足すようにした（5件→35件、脇役の人物紹介で29件→56件）。

### 3.21 見出しかどうかを行の長さから推し量っていた

「魔法少女それぞれが魔女化した魔女の名前」を尋ねた回答が、**巴マミの魔女とほむらの魔女を
同じ「此岸の魔女」として**述べた。原文を見ると、こう並んでいる。

    此岸の魔女
    ゲーム版における暁美ほむらが魔女化した存在。
    おめかしの魔女 / キャンデロロ（Candeloro）
    巴マミが魔女化した存在。性質は「ご招待」。

`heading_of` は「短く、句読点が無く、文末記号で終わらない行」を見出しとみなしていた。
上限は26文字。「おめかしの魔女 / キャンデロロ（Candeloro）」は28文字なので見出しと認められず、
本文として扱われ（文末記号が無いので断片として捨てられ）、**節は1つ前の「此岸の魔女」のまま**
次の行へ引き継がれた。結果、マミの魔女の説明がほむらの魔女の節に入った。

回答の誤りは知識層の誤りであって、モデルは与えられた材料の通りに答えていた。

見出しかどうかは推し量るものではなく、HTMLに書いてある。`html_to_text` が
`h1`〜`h6` と `dt` を `## 見出し` の形で残すようにし、印のある行は長さを見ずに
見出しとして扱うことにした（上限は90文字の安全弁のみ）。見出しの中にはアンカーや
リンクが入るので、表のセルと同じように中身を溜めてから1行にまとめる。

### 3.22 主張IDを原文の並び順として使っていた

「同じ出典から取り出した主張は、claim ID の小さい順が原文での並び順に対応する」という
前提で、節の切り出しも回答プロンプトの指示も書いていた。これは**一度きりの取り込みでしか
成り立たない**。抽出の条件を変えて同じ出典を取り直すと、原文の途中にある文が後から
末尾のIDで入るので、IDの順は原文の順とずれる。実際、再取り込み後は魔女の節の記述が
記事の末尾に並んでいた。

`claims.offset`（原文中の位置）を足し、抽出時に控えるようにした（スキーマ版3）。
既存のDBは `examples/backfill_offsets.py` が locator から位置を復元する。

### 3.23 人物名を含まない文を、ほぼ全部捨てていた

抽出は既定で「登録済みのエンティティに触れる文」だけを主張にしていた。作品を説明する
ために書かれた資料では、これが致命的になる。用語・設定・各話・制作の経緯・魔女の性質は、
人物名を含まないことのほうが多い。実測で候補の38%（各作品2000件前後）が落ちていた。

出典種別で分けることにした。Wiki・公式サイト・書き起こし・画像の読み取りは、
ページ全体が作品の説明なので人物名の無い文も採る。ニュース記事や感想noteは
案内と余談が大半なので、従来どおりエンティティに触れる文だけを採る。
あわせて、Wikiの「出典」「注釈」「参考文献」節（書誌情報が並ぶ）は主張にしないようにし、
節見出しがある場合は短い文（「性質は「ご招待」。」）も採るようにした。

### 3.24 数え上げの質問に、連続した1区間では答えられない

3.14で「渡すのは連続した一区間」としたが、「魔法少女それぞれの魔女化」のように
**答えが1か所にまとまっていない**質問がある。1つの記事の中で、人物ごと・用語ごとに
離れた場所に少しずつ書かれている。1区間だけ切り出すと最初の1人分しか渡せない。

出典ごとの持ち分（24件）を、重ならない複数の区間（8件×3）に分けて使えるようにした。
1つの話題に答える質問では上位の区間が隣り合って実質1区間になり、数え上げの質問では
離れた場所に散る。あわせて、先頭の枠（全体の4割）は同じ節から3件までとし、
「広さは先頭、深さは区間」という分担にした。

### 3.25 それでも、数え上げの質問は語の一致だけでは解けない

上記を入れても、「魔法少女それぞれの魔女化」で主要5人の魔女を揃えるには足りなかった。
この記事には40以上の魔女が同じ書式で並んでおり、質問文には「魔法少女」としか書かれていない。
**どの5人を指すのかが質問に書かれていない以上、語の重みでは区別できない**。

質問→検索語のLLM前処理（ブラウザUIのみ）に、まとまりを指す質問ではその一人ひとりの名前と、
資料が使う定型の言い回し（「〜が魔女化した存在」「性質は」）を挙げるよう指示を足した。
実測では、前処理が人物名を返した場合も定型句を返した場合も7つの魔女が揃う。前処理が
無い場合（`cqs ask` にAPIキーが無い等）は3つにとどまる。ここは未解決事項として残る。

### 3.26 資料を増やすと、定型文が枠を食い始める

出典を85件まで増やしたところ、「まどかはどんな願いを叶えた？」の材料の先頭が
「願いを叶えた代償として『魔法少女』となり……」という作品紹介の定型文で埋まった。
この一文はあらすじを載せるほぼ全ての出典に、少しずつ違う形で載っている。
出典が増えるほど、同じ内容の主張が枠を食い潰す。

文字3組の重なりで近さを測り、近すぎる主張は1件だけ残すようにした。
重なりは「短いほうのうち何割が相手に含まれるか」で測る。同じ定型文でも前後に足す
言葉は出典ごとに違うので、両方の長さで割ると（Jaccard）実測0.35〜0.42にしかならず、
同じ文として拾えなかった。

### 3.27 出典ごとに「どこまで取り込むか」を持たせた

監督・脚本・声優・音楽家の記事を足すと、その人の他作品の話が大量に入る。
3.23で「参照系の出典は人物名の無い文も採る」としたが、これらは Wikipedia でありながら
**作品そのものの資料ではない**。`sources.extract`（full / entity_only / 未指定）を足し、
出典ごとに指定できるようにした（スキーマ版4）。未指定なら従来どおり出典種別で決まる。

実測では、悠木碧の記事（12.8万字）から入った主張は146件、虚淵玄の記事は17件に収まった。

### 3.28 取り出しの単位が「出典の一区間」では、節の説明が届かない

「それぞれの魔女化」を尋ねた回答が、一行だけの表（「人魚の魔女 / 真名 Oktavia / 性質 恋慕」）
から組まれていた。Wikipediaのキャラクター一覧には結界・姿・攻撃方法まで15件の記述があり、
知識層にも入っているのに、回答へ渡ったのは1件だけだった。

3.14で導入した「幅の決まった窓を出典の上で滑らせる」やり方には、構造的な偏りがある。
**一行ずつ並んだ一覧表は、どの行にも語が当たるので必ず密に見える**。一方、説明の書かれた節は
当たる行が少ない。窓の当たりの量で比べると、表が必ず勝つ。

取り出しの単位を「節」に変えた。参照記事は人物や用語ごとに節が立っており、
「それぞれの〜」と尋ねたときの答えは節そのものだから。節だけでは当たりの無い節に
手が届かないので、「出典まるごと」も擬似的な節として候補に残している
（「時系列まとめ」のように出典そのものが答えである場合のため）。

あわせて3つ直した。

- **群の点数は「実際に渡す分」で測る**。群の全体を合計すると、見出しが1つしかない長い記事
  （187件で1節）が件数だけで勝つ。渡すのは10件なので、その幅の窓で比べる。
- **1件の重みに文の長さを掛ける**。表の一行と説明文を同じには数えない。
- **節の見出しが登録済みの対象そのものなら押す**。「人魚の魔女 / オクタヴィア」は
  問われている当の対象の説明そのもの。「劇場版〈…〉あらすじ」は同じ語を含んでいても対象ではない。
  エンティティは人が選んで登録したものなので、その目印になる。

### 3.29 見出しの割り引きが、節を選ぶ段でも効いていた

3.13で「見出しだけの一致は本文の1/4」にした。名言集の対策としては正しいが、
**節を選ぶ段でこれを効かせると逆を向く**。「人魚の魔女 / オクタヴィア: 上半身は鎧兜を
まとった騎士で……」の説明文は魔女の名前を繰り返さない。だが、その節は問われている当の対象に
ついての記述そのものである。割り引いたまま節を選ぶと、この節が丸ごと沈む。

割り引く前の点を別に持ち、主張を1件ずつ並べる先頭の枠では割り引いた点を、
節を選ぶ段では割り引かない点を使うようにした。実測で、質問に魔女名が含まれる場合、
人魚の魔女の節から渡る件数が1件から6〜7件になった。

### 3.30 一発検索では「それぞれ」に答えられない（多段のリサーチ）

ここまでの直しはすべて「1回の検索でどう良い材料を選ぶか」だった。だが
「それぞれの魔女化は？」と「人魚の魔女について詳しく教えて」を比べると、
**同じ知識層から、後者だけが厚い答えを返す**。材料が無いのではなく、
1回の検索では対象を分けられないだけだった。

    人魚の魔女について詳しく教えて  → 真名・性質・結界・姿・攻撃・使い魔・各作品での結末
    それぞれの魔女化について教えて  → 真名と性質が数行

どの一人ひとりを指すのかが質問文に書かれていない以上、語の重みでは区別できない。
120件の枠が一覧表と概要文に薄く広がって終わる。**枠が足りないのではなく、配り方の問題**である。

段を分けた。

1. 質問を読んで、複数の対象をまとめて尋ねているなら対象を挙げる（LLM。
   登録済みエンティティの一覧を渡し、その名前を使わせる）
2. 対象ごとに枠を分け、対象の名前を足して引き直す
3. 対象ごとに見出しを付けて1つのプロンプトにまとめ、項を立てて答えさせる

実測（6対象）で、真名・性質・デザインが6体すべて揃うようになった。
1対象あたり6〜20件で、合計は従来と同じ120件以内に収まる。

あわせて、**どれくらいの深さの答えが要るか**も同じ段で決めるようにした。
point（1つの事実）なら枠を半分にする。「監督は誰？」に120件を渡すと、
周辺の話に埋もれて答えがぼやけるため。

APIキーが無い場合はこの段が丸ごと飛び、従来どおりの一発検索になる。

### 3.31 1回の質問で終わらせない

知識ベースは、訊き方を知っている人ほど深く掘れる。「人魚の魔女について詳しく」と
訊けることを知らなければ、厚い答えには辿り着けない。

回答のあとに、次に訊きそうなことを5つ出すようにした。回答が「この知識層には無い」で
終わった点や、触れただけで掘り下げていない点を優先させ、登録済みの固有名詞を使わせる
（知識ベースに答えがある見込みが高くなる）。押すとそのまま次の調査が始まる。

### 3.32 特定の提供元に縛らない

回答生成・質問の計画・画像の読み取りで anthropic のSDKを直接呼んでいた。一般に配布する
道具としては、**検索部分が特定のサービスの利用者に限られる**形になってしまう。

呼び出しを `cqs/llm.py` の1か所にまとめ、**OpenAI互換のAPI**（OpenAI本体、LM Studio、
Ollama、vLLM、各種ホスティング）と **AnthropicのMessages API** のどちらでも動くようにした。
どちらも標準ライブラリのHTTPで叩くので、`[llm]` の追加依存（anthropic パッケージ）は不要になった。

提供元は環境変数から自動で決まる（`CQS_LLM_BASE_URL` か `OPENAI_API_KEY` があれば
OpenAI互換、`ANTHROPIC_API_KEY` があれば Anthropic）。ローカルのサーバはキーを
要らないことが多いので、基点だけでも動くようにしてある。

**LLMが無い状態を「機能制限」ではなく正式な使い方として扱う**ことも、あわせて明記した。
`cqs ask` は材料とそのまま貼れるプロンプトを出す。出典・確認状態・区分の扱い方は
プロンプトに全部入っているので、貼られた側は同じ制約で答える。
MCPサーバーとして使う場合も、検索はこのシステムが行い回答は繋いだ側が書くので、キーは要らない。

検査は、OpenAI互換とAnthropicの応答をまねる小さなHTTPサーバを立てて行っている
（本物のAPIは叩けないため）。送信するJSONの形、鍵の載せ方、画像の包み方、
前置き付きの返事からJSONを取り出せるかを見ている。

### 3.33 UIに作品固有の文字列が焼き付いていた

ページの見出しが「超かぐや姫！ 知識ベース」で固定されており、作品を切り替えても
変わらなかった。質問欄のプレースホルダも「例: かぐやと彩葉の関係は？」のままだった。
2作品目を入れるまで気付かない類の作り込み漏れで、**道具の名前と中身の名前を混ぜていた**のが原因。

題名はシステムの名前で固定し、いま見ている作品はその後ろに添えるだけにした。
プレースホルダは、選んでいる作品の登場人物から毎回組み立てる。
ブラウザUI（`cqs serve`）側にも同じ問題があったので直した。

## 4. 未解決事項（設計メモ11章の現状）

### 4.1 公式サイトの再取得頻度

### 4.2 矛盾検出の機械化

未実装。現状は人が `claim link A contradicts B` で結ぶ。
同一エンティティ内の相反する主張を自動で見つけるには意味の比較が要るので、
LLMに定期的に走らせるのが現実的だが、誤検出のコストが不明なため保留にした。

### 4.3 X（旧Twitter）はタイムラインを辿れない

FxTwitter API 経由で、プロフィールと**個別の投稿URL**は取得できるようになった
（`https://x.com/<user>` と `https://x.com/<user>/status/<id>`）。

残る制約は、**アカウントの投稿一覧を辿れない**こと。FxTwitter にタイムラインを返すエンドポイントが無いため、
どの投稿を取り込むかは人が投稿URLを渡して決めるしかない。公式アカウントの告知を漏れなく追う用途には足りない。

また、告知の投稿は装飾記号と改行が主体で、文として成立する行が少ない。
今回取り込んだ公式SNS6件から機械抽出できた主張は4件にとどまった。本文自体は原文層にあるので検索では引ける。

Netflix の作品ページは JavaScript で描画されるため、取得しても本文が得られない。
ブラウザを使う取得は実装していない。

### 4.4 ベクトル検索

設計どおり未実装。合図（「全文検索で当たるはずの原文が、表現違いのせいで見つからない質問が実際に出た時」）も
そのまま据え置く。現時点ではその事例を観測していない。
